# Equivalence reports, data tables, overlays

## When to prepare a report

Whenever the converted model will be relied on by someone who did not run the
conversion. It is the artefact that makes a conversion reviewable: a report
living only on one laptop cannot be reviewed by the team depending on it.

The bundled report covers the structural model, with every random effect at
zero. Population equivalence is a separate claim and needs separate measured
evidence; a validated overlay alone does not establish it.

Link every item that exists. A report linking a model but not the trial it was
verified on is harder to trust than one linking both.

## What Jinkō's document renderer does to markdown

Two things, and both are silent.

**It discards every table's header row.** The published "Renamed symbols"
table came out with four unlabelled columns, so nothing said which held the
Jinkō name and which the reason. A table whose header is *already* blank
renders its body correctly, so the publisher emphasises the headings and
demotes them to the first body row on the way out. The local markdown file
keeps a proper header: it is the renderer being accommodated, not the report.

**A bare Jinkō URL alone in its paragraph becomes a project-item card**,
carrying the item's name, type and metadata badges. Anything else on the line
-- a label, a bullet, link syntax -- and it stays a plain link. That is what
the converted-items list uses; a table of links carried none of that metadata
and was mangled besides.

## Publishing

`publish_equivalence_report.py` uploads the Markdown as a Jinkō document,
uploads the referenced plots as images, rewrites local image targets to their
uploaded URLs, and prepends a linked index of the converted items. `https`
targets are left alone.

Local images must be relative paths contained below the report directory.
Absolute paths, parent traversal, and symlinks escaping that directory are
rejected. `--comparison` must name passing measured comparison JSON. Dry-run
prints a digest binding those metrics, the report, images, destination, and
linked item SIDs; apply requires that exact value through `--approve-digest`.

`--json-out` writes the created document's SID and URL. `--out` writes the
assembled markdown locally as well, and refuses to overwrite without
`--overwrite`.

Generic document mechanics belong to `jinko-document`.

## Data tables

`upload_data_tables.py` builds two tables from one solved trial.

**Individual** — one row per patient, per arm, per time, unchanged.
`experimentRef` names the patient so profiles stay separable.

Neither is reported on the solver's own grid. That grid is uniform, which
spends most of its points on a flat elimination tail and too few on absorption,
and it is fine enough that a twelve-arm trial's individual table reaches a
quarter of a million rows. `--time-points` chooses instead: about ten for a
single dose, up to forty for a multiple-dose profile, keeping every
administration time, the peak after each of them, and the tail. `0` keeps the
solver's grid.

**Summary** — one row per arm and time: the median with wide bounds at the
2.5th and 97.5th percentiles. Point-value rows with wide bounds, which is what
a visualisation overlays and a calibration objective scores against. Reports
`validForFitnessFunction: true`, so it doubles as a calibration target.

The schema requires `wideRangeLowBound < value < wideRangeHighBound` strictly. A
population is degenerate at the moment of dosing, so those rows are dropped and
the drop reported. Inventing an interval around a known-exact zero would be
scored as evidence during a calibration.

A large individual table -- one row per patient, per arm, per time, over five
arms and sixty patients -- runs to tens of thousands of rows and can have its
connection dropped mid-upload. That failure says nothing about the conversion;
retry it. `--skip-individual` uploads only the summary when the individual
profiles are not wanted.

A retry is safe when `--json-out` recorded each upload as it landed. Reuse is
allowed only from a ledger naming the same source trial; display names are not
identities and are never used to select a table. Before reuse, every recorded
row is compared with the table generated by the current outputs, units,
percentiles, and sampling grid. `--force-new` ignores the ledger and uploads
another deliberately. If a response was lost before its SID could be recorded,
inspect the project and supply the intended SID explicitly rather than accepting
a same-name guess.

Generic table mechanics belong to `jinko-data-table`.

## Attaching a data table

**The trial carries the data tables, not only the visualisation.** A trial has
a `dataTableDesigns` list, and that is where the platform binds a table and
where a calibration objective reads one from. Setting a visualisation's
`dataOverlay` alone left both the trial and the visualisation showing no data,
which is indistinguishable from success unless somebody looks. Bind the table
to the trial *and* name it in the overlay.

A design entry's `options` are not optional. `"options": {}` is accepted and
then displays nothing: the `label` is what identifies the table wherever it is
drawn or scored. The platform's own form replaces every character that is not
a letter, a digit or a hyphen with an underscore, so "acop — population
summary" becomes `acop___population_summary`. Write `logTransformWideBounds`,
`timeTolerance` and `weight` too.

A visualisation's `timeUnit` is `"h"`, not `"hour"`. The overlay's times are
read in it.

An explicitly supplied summary table is compared row-by-row with the summary
generated from this trial before binding. A failed rerun, false
`validForFitnessFunction`, or unresolved overlay diagnostic makes the command
exit nonzero while preserving the partial ledger.

**Binding costs a re-run, and the order matters.** Patching a trial's
`dataTableDesigns` creates a new trial snapshot, and a new snapshot has never
been launched -- so the results the table was *built from* stop resolving the
moment the table is attached, and the trial's status reads "not launched". The
script re-runs it, which is quick because nothing about the solve changed: a
data table is scoring input, not model input. `--no-rerun` skips that and says
what it leaves behind.

I got this wrong first: bound the tables to nine completed trials and reported
it as done, without checking that a patch invalidates a run. All nine had to be
re-run.

## Overlays

The visualisation field carrying data tables is `dataOverlay`. The neighbouring
`overlay` is an `IndividualPatientsOverlay` and rejects the shape.

**A visualisation warns about any selected output the overlay has no rows for,
and that warning is the only signal** — the plot renders exactly as though no
data had been supplied. Cover every output the visualisation displays, not just
the one of interest, and read the diagnostics rather than trusting the picture.

`obsId` must name a real trial output and `armScope` a real arm. Both are
checked before upload.

An existing visualisation is patched, not rewritten, so its panel configuration
survives.

Generic visualisation mechanics belong to `jinko-trial-viz`.
